1. 问题与事实

1.1 三边现状

维度 线上（现网） 原型（本仓库） 提成设置
归属概念 大类（项目分类 / 产品分类） 自定义分组 + 系统「隐藏」组 「整组」= 分组（{kind:'group'}）
基数 必选 可选、可空（条目可为 0 个分组） —
重数 1:1（一个条目属于 1 个大类） N:N（可属多组） 规则可命中多条
可改 不可改（前线诉求「大类选错可改」） 随时可改（含全部取消） —
category 字段 有效、用户可见 仍在数据模型里，但写死常量（项目「其他」/ 产品「产品」） —
解析规则 — — 实测 先写先赢（见 §1.2）

线上「分组选择」（ProjectGroupSelectFragment）经确认只是大类的另一个叫法，同一份数据 —— 因此线上不存在"多归属分组"这一既有能力；原型引入的是全新能力，迁移是干净的 1:1 映射，无需合并两套分组。

1.2 实测证据：提成不是「取高」，是「先写先赢」

直接调用 Comm2Demo.calcStaffTrial 打真实试算链路（试算行 深层补水护理 / p21 / 原价 268 / 员工 st0）：

场景 覆盖项书写顺序 实际计提 生效费率
A 两条覆盖都指向同一个具体项目 5% 在前，20% 在后 13.4 5%
A 同上 20% 在前，5% 在后 53.6 20%
B 两条覆盖各指向一个分组（项目同属两组） 5% 在前 13.4 5%
B 同上 20% 在前 53.6 20%
C 分组覆盖(40%) vs 具体项目覆盖(5%) 分组在前 107.2 40%
C 同上 项目在前 13.4 5%

结果完全随书写顺序翻转。 根因（提成设置/comm2.js）：

resolveLineBlock(sch, line)   // L1620
  for (ov of sch.overrides)                 // 顺序遍历
    for (t of ov.targets)
      if (t.kind === 'group' && lineInGroup(line, t, gk)) return ov;   // 第一条命中即返回
  • 「取高」只存在于跨方案层：calcStaffTrial 里 if (!winner || c.amount > winner.amount)（L1866，严格大于 → 并列取列表中更靠前的方案）。
  • 用户新增规则项走 sch.overrides.push(...)（L2377，追加到末尾）；unshift 仅用于系统「快捷开单」（L342，故意置顶）。
  • 覆盖列表无拖拽排序、无命中来源显示、无冲突提示。

连带隐患：删除分组后，指向它的规则 lineInGroup 里 find 不到 → 静默不命中 → 回落默认卡，金额可升可降，全程无提示。

与文档的矛盾（需一并修正）：PRD / 帮助弹窗写的「好几张卡都管到同一个项目 → 挑钱多的那张算」「单独加的规则项更优先」—— C 场景证明覆盖之间的"更优先"不成立。

1.3 若不做本方案会发生什么

后果 说明
分类塌缩 按原型直上，存量 category 全部写入「其他」/「产品」，报表与导入导出失去维度
提成真空 分组可空 → 出现无归属条目，提成从"必有类规则覆盖"退化为可能只吃默认卡
提成不可解释 多归属使重复命中概率大增，而规则是"先写先赢" → 改费率"没反应"、加规则"不生效"
无声改钱 归属从"改起来很麻烦"变成"点两下"，且删组会静默废掉规则

2. 决策记录（本次拍板）

# 议题 决策
D1 大类去留 大类 → 「主分组」：必选、1:1、可改，用于统计 / 导入 / 默认筛选；另可自由加自定义分组（多归属）
D2 重复命中规则 显式优先级链：具体项目/产品 > 分组 > 默认卡；同层取高；并列按规则项顺序
D3 变更护栏 允许改，仅 toast 轻提示（不阻断、不弹确认）
D4 分组变更的生效口径 不弹窗、即时生效、固定 forward：分界时刻之后按新分组算；仅一条 toast 告知（文书 §7）。不再复用"本期全部重算 / 从现在起用新方案"两枚按钮 —— 那条路径属方案规则改动（D8），本决策不涉及
D5 线上「分组选择」 即大类的同义叫法，同一份数据；迁移为 1:1
D6 下游依赖 经营分析/报表 · 开单选品 · 会员卡权益选品 · 库存（导入导出、商城/联盟侧本次判定为不依赖）
D7 上线方式 一次性全量替换
D8 方案规则改动的重算弹窗 保持不动 —— 方案 defaults / overrides / stationIds / stationLabels 改动仍走既有 #comm2RecalcMask（两枚竖排按钮，二十七～三十二次定稿）
D9 术语口径 替换上线后，其他地方关于项目/产品「类」的描述统一改为「组」（§11）
D10 线上会员卡「计次卡」的适用范围 由线上「1 个大类」改挂 1 个主分组（primaryGroupId 轴，不引用自定义分组）；模板层实时跟随、办卡实例层快照冻结；绑卡派生取 模板 ∪ 持卡实例 并集（§12）

D3 + D7 的代价：没有灰度观察期、又没有阻断，因此上线前体检（§9.1）+ 回滚包（§9.2）+ 上线后核对（§9.3）是硬性补偿项，不可省略。

D4 的代价：分组变更没有"重算历史"的退路，且用户无法在不生效的前提下试改。因此「分界记录」是必需项而非可选项（§7.1 给出理由与实现）。

D10 的代价：适用范围从"写死在模板上的 1 个大类"变成"跟随分组成员"，于是分组一动，绑卡面就跟着动 —— 整组项目会被一次性锁成不可删。这是 D10 为换取「语义零漂移」必然付出的代价（只有 1:1 的主分组才能让判定无歧义），但必须配套 §12.5 的商户告知与并集绑卡，否则历史卡会出现孤儿引用。

3. 目标数据模型

3.1 分组 CatalogGroup（在原型基础上扩展）

字段 类型 新增 说明
id string 桶内唯一
name string 桶内唯一；系统组不可改名
itemIds string[] 组成员
order number 轨内顺序
system boolean 系统组：不可改名 / 不可删 / 不参与提成目标
systemKind 'hidden' \| 'fallback' ✅ hidden = 隐藏组；fallback = 主分组兜底组（§3.3）
source 'category' \| 'custom' ✅ 迁移来源标记（仅作追溯与回滚用，UI 不展示）
_prevItemIds string[] | null ✅ 归属分界 · 变更前成员快照（D4）。仅在成员集发生变化时写入；无变更时为 null
effectiveAt string | null ✅ 归属分界时刻（YYYY-MM-DD，与订单行 ymd 同格式）。ymd < effectiveAt 的行按 _prevItemIds 解析，>= 按 itemIds 解析
effectiveKind 'member' ✅ 分界来源（当前只有成员变更一种；为后续扩展留位）

与方案侧 _prev 的分工：方案侧 _prev 快照的是规则集（defaults / overrides / …），分组侧 _prevItemIds 快照的是成员归属。两者同模式、可叠加：同一行先按 schForLine 取当时方案，再按 lineInGroup 取当时成员集（§7.3）。

桶结构不变：state.catalogGroups = { project: [...], product: [...] }。

3.2 项目 / 产品（在原型基础上扩展）

字段 类型 说明
primaryGroupId string ✅ 新增。主分组 id；非空，且必须 ∈ groupIds
groupIds string[] 归属的自定义分组集合（含 primaryGroupId；不含系统「隐藏」组）
category string 迁移期保留只读兼容（§4.3），新写入不再依赖；下线时机见 §11
hidden boolean 保持与系统「隐藏」组成员双向同步（不变）

3.3 不变量（Invariants，必须由服务端与前端共同保证）

  1. primaryGroupId 恒非空且恒存在于同桶分组表。
  2. primaryGroupId ∈ groupIds（勾选里取消不掉主分组；取消主分组需先改指另一个）。
  3. 每个桶至少存在一个 systemKind:'fallback' 分组（项目「其他」/ 产品「产品」），不可删除、不可改名、不可设为隐藏。
  4. 系统「隐藏」组不入 groupIds、不可作为主分组、不可作为提成「整组」目标（现 getCustomCatalogGroups() 已按 !g.system 过滤，保持）。
  5. 删除分组时，若它是某些条目的主分组 → 必须先指定迁入分组（默认指向 fallback 组），再删；指向它的提成规则必须提示（§6）。
  6. 归属分界单调：effectiveAt 一旦写入即为当前分界点，后续再改会覆盖它（不做多段历史）。写入时必须同时落 _prevItemIds（覆盖前成员集）与 effectiveAt（本次变更时刻），二者同生同灭 —— 单独存在任一项即为脏数据。
  7. 迁移初始：_prevItemIds = null / effectiveAt = null（迁移本身是"无前史"的起点，不产生分界，不触发 toast）。

3.4 映射（线下 → 新模型，1:1）

线上 新模型
大类 c 分组 { id: 'g_'+c.id, name: c.name, order: c.order, source: 'category' }
条目 it.category === c it.primaryGroupId = 'g_'+c.id；it.groupIds = ['g_'+c.id]
无分类/空分类条目 指到本桶 fallback 组
线上「未分类」占位（若有） 与 fallback 组合并，不新建

4. P0 数据迁移

4.1 步骤（幂等、可回滚）

  1. 冻结写入（价目与提成两侧短时只读窗口）。
  2. 为每个桶建分组表：先建 fallback 组，再按大类顺序建 source:'category' 组（保留原排序与名称）。
  3. 回填 primaryGroupId / groupIds（按 §3.4）。
  4. 校验通过后才切读：见 §9.1 体检项全绿。
  5. 解冻。

4.2 回滚包（一次性全量的必需品）

  • 保留 category 字段原值（不覆盖），并落一份 迁移映射表（groupId ↔ categoryId）。
  • 保留迁移前价目全量快照（条目 + 大类 + 排序）。
  • 回滚动作：切回读 category + 隐藏分组入口；primaryGroupId/groupIds 保留但忽略。回滚不需要反向写数据，因此是双向安全的。
  • 提成侧回滚：source:'category' 分组与原型分组同构，规则无需回滚；但若已按 §5 上线新解析，需一并回退代码版本。

4.3 category 字段兼容期

  • 迁移后 category 只读保留，不参与任何计算与展示（除 §9.3 核对）。
  • 下线时机：至少跨过一个完整结算周期，且在 §9.3 抽样核对全绿之后（见 §13 待确认）。

5. P1 提成优先级链（替换「先写先赢」）

5.1 分层

层 目标类型 说明
L1 {kind:'project' \| 'product' \| 'card'}（具体标的） 含系统「快捷开单」（refId=COMM2_QUICK_REF，保持最高优先）
L2 {kind:'group', groupKind}（分组） 「整组」
L3 sch.defaults[cat]（默认卡） 兜底

5.2 解析算法（替换 resolveLineBlock 的单命中语义）

candidates = []                       // 收集，不再 return
for ov in sch.overrides (index asc):
  for t in ov.targets:
    tier = (t.kind === 'group') ? 2 : 1
    if matches(t, line):               // 项目/产品/卡 或 lineInGroup
      candidates.push({ ov, tier, index })

if candidates empty:
  if isQuickLine(line): return 系统快捷开单覆盖
  return sch.defaults[cat]             // L3

minTier = min(candidates.tier)         // 取最具体的那一层
tiered  = candidates.where(tier === minTier)

eligible = tiered.where(试算可计提)     // scope 通过（§5.3.1）
if eligible empty: return tiered 首条    // 保持现状：命中即不回落默认卡
winner = eligible 中 amount 最大者；并列取 index 最小者
return winner.ov

要点： - 分层的判据是"目标具体程度"，与费率高低、添加先后无关 —— 这直接修掉 §1.2 的 C 场景（分组 40% 再也压不过具体项目 5%）。 - 同层取高用试算金额比较（不是费率），与跨方案层一致；并列按规则项顺序，与现文档「钱一样多时按先后」自洽。 - 跨方案层不动（calcStaffTrial 的严格大于 + 并列取靠前方案）。 - 需要在 schemeLineAmount 内改为"对候选集逐块试算再选"，即把现有单块计算抽成 amountOfBlock(sch, block, line) 复用（sign 分支同样要走）。

6. P2 分组变更提示（D3 + D4：不弹窗、仅 toast）

6.1 总原则

分组归属变更（含成员增删、删组、改主分组）一律即时生效、无弹窗、无二选一；是否提示取决于该分组是否被提成规则引用 —— 未被引用则完全静默（改一个没人用的分组不该打扰用户）。

6.2 触发矩阵与文案

入口 弹 toast 的条件 文案
包含项目 / 包含产品页 · 确定 本次变化的任一分组被 ≥1 条提成规则引用 分组已更新 · 之后的提成按新分组计算
条目详情 · 改主分组 主分组（旧或新）被 ≥1 条提成规则引用 同上
分组管理 · 删除分组 该分组被 ≥1 条提成规则引用 「X」已删除 · N 条提成规则不再生效
分组管理 · 重命名 从不（id 不变，提成不受影响） —
分组管理 · 新建分组 从不（新组尚未被引用） —
任一入口 · 分组未被任何规则引用 从不 —

文案定稿（简明扼要，与现有 toast 同规格）

  • 成员变更 / 主分组变更：分组已更新 · 之后的提成按新分组计算（16 字，单行）
  • 删组：「X」已删除 · N 条提成规则不再生效（N = 引用该组的规则项数）

两条文案都只说结论、不说原因，且不出现"本期"字样 —— 因为生效粒度是按单据日期而非"按期"（§7.1），写"本期"会与"已结的单不改"冲突（见 §7.2）。

6.3 残余风险与强制补偿

轻提示不阻断，因此以下两点为强制补偿：

  1. 删组保护：若该分组被提成规则引用，删除确认弹窗必须列出规则名（一次性、可跳过，但必须出现一次）。
  2. 规则失效可观测：进入方案编辑页时，对"引用了已删除分组"的规则项标红并提示「目标分组已不存在，该规则不会命中」—— 修掉 §1.2 的静默失效隐患。

与旧版（v1.0）的差别：原「包含项目/产品页确定」文案 已更新成员 · N 个项目的提成将变化 作废 —— 它只说了"会变"、没说"从何时起"，且"将变化"与"即时生效"语义冲突。

7. P3 生效口径（D4：不弹窗、自动 forward）

7.1 为什么「分界记录」是必需项

关键事实：薪资侧不是"读存量"，而是每次缓存失效都重算 —— 提成设置/employee.js：

finalizeSeedCommLines(lines, staffId)
  → C.calcStaffTrial(staffId, trialPayload, state.salaryMonth)      // L3511-3512
  → 每行载荷带 { ymd: ln.ymd }                                      // L3509（二十六次为 forward 加的）

而 invalidateCommLineCache() 在仓库中被调用 30 余处（切月份 / 员工变更 / 方案保存 / 归属变更…）。

因此：若只加 toast 而不落分界，之后任何一次缓存失效都会用新分组把当期金额静默重算 —— toast 说的"之后的提成按新分组算"当场失真，且用户不会察觉。

实现（复用方案侧既有 _prev 模式，零新增 UI）

lineInGroup(line, target, groupKind):
  g = comm2Groups(groupKind).find(x => x.id === target.refId)
  if (!g) return false
  members = (g.effectiveAt && line.ymd && line.ymd < g.effectiveAt)
              ? (g._prevItemIds || [])
              : (g.itemIds || [])
  return members.indexOf(line.refId) >= 0
  • 改动面 = 1 个函数 + 2 个字段 + 3 处写入点（包含项目/产品页确定 / 删组 / 改主分组）
  • line.ymd 已在试算载荷里（二十六次为方案侧 forward 引入），无需新增管线
  • 与 schForLine(sch, periodKey, ymd) 同思路、可叠加（§7.3）

7.2 生效粒度与边界

情形 口径
分界时刻之后的单据 按新分组算
分界时刻之前的单据 按旧分组算（_prevItemIds）
已结算 / 历史期 不回算（与 v1.0 的"迁移当天不回算"一致，继续成立）
人工改过的提成值 恒优先，任何重算都不覆盖（沿用现状：_manualPreserve）
迁移当天 effectiveAt = null → 不产生分界 → 全部按迁移后分组表算；迁移不弹 toast
连续多次改动 覆盖上一个分界点，不做多段历史（§3.3 不变量 6 已标注）

7.3 与方案侧重算弹窗的关系（D8，互补不冲突）

改动类型 机制 用户交互
分组归属（成员 / 主分组 / 删组） 分组侧 _prevItemIds + effectiveAt 无弹窗，仅 toast（§6.2）；固定 forward
方案规则（defaults / overrides / stationIds / stationLabels） 方案侧 _prev + effectiveMode + effectiveAt（二十七～三十二次定稿） 既有 #comm2RecalcMask 两枚竖排按钮（recalc / forward）本次不动

两者按同一行日期独立解析后叠加，一行金额的实际取数链：

calcStaffTrial(staffId, lines, periodKey)
  → 每行: schForLine(sch, periodKey, line.ymd)     // 方案侧：老/新规则集
  →       schemeLineAmount(sch, line)
  →         resolveLineBlock(sch, line)            // §5 优先级链（本次修改）
  →           lineInGroup(line, t, groupKind)      // 分组侧：老/新成员集（§7.1）

即：方案侧决定"用哪套规则"，分组侧决定"这条规则管不管这个项目"，两者各按行日期取值，互不干扰。

9. 上线预案（D7：一次性全量）

9.1 上线前体检（dry-run，必须全绿）

  1. 归属完整性：primaryGroupId 非空率 = 100%；primaryGroupId ∈ groupIds 违反数 = 0。
  2. 映射一致性：条目数、名称、价格、onSale、hidden、排序，迁移前后逐条 diff = 0。
  3. 分组数核对：新分组数 = 原大类数 + 1（fallback/桶）。
  4. 提成影响报告（最重要）：对全部方案重放试算，输出 - 因优先级链改变而金额变化的（规则项, 试算行, 变更前 → 变更后）； - 因分组可空而从"类规则命中"退化为"默认卡"的条目清单； - 引用了不存在分组的规则项（即已静默失效者）。 此报告需逐条人工确认后放行。

  • 监控：primaryGroupId 空值率、指向不存在分组的规则项数、提成人工修正率（环比突增即为异常信号）。

12. 会员卡 · 计次卡（大类 → 分组）

为什么单独开章：这条链路不在 §8「下游回归」的射程内 —— 它不是只读选品，而是存了一份归属引用。用户澄清：线上会员卡系统里有一种 「计次卡」，每个卡模板可选 1 种「大类」作为适用范围（该大类下的项目都可用这张卡扣次）；它不是本仓库新原型的「独立计次 / 关联计次」（那两者用的分别是卡名与显式项目清单）。因线上会员卡不在本次同期下线（两线并行），这份引用必须随价目表迁移同步改造，否则价目一完成切换，计次卡的适用范围就指向了不存在的枚举。

12.1 现状与牵动点

侧 计次卡的「适用范围」怎么存 本次牵动
线上会员卡（现网） 模板存 1 个「大类」（枚举值） 「大类」在价目侧被升级为「主分组」（D1）→ 引用轴必须换
本仓库新原型 「独立计次」适用范围 = 卡名（只读，写入 simpleTimesProjectName）；「关联计次」= 显式项目清单（§6.3.2 / §6.4） 本次不动（§1.5 已把线上次卡映射到「项目」权益；本条只覆盖线上线）
价目表（迁移后） 分组表 catalogGroups.{project,product}；条目有 primaryGroupId（1:1）+ groupIds（N:N） 提供新的引用轴

关键前提：线上「大类」是 1:1（一个项目属于且仅属于一个大类），而新模型里只有「主分组」保持这一性质 —— 自定义分组是 N:N。

12.2 决策

# 议题 决策
D10-a 引用哪条轴 只引用「主分组」（primaryGroupId 轴）；不允许引用自定义分组
D10-b 单选 / 多选 单选 1 个（与线上「1 个大类」严格 1:1）
D10-c 生效口径 模板层实时跟随（live）；办卡实例层快照冻结
D10-d 绑卡派生 必须取 模板（scopeGroupId → 组成员）∪ 持卡实例快照 的并集
D10-e 绑卡后果 沿用价目表 PRD §4.3：不可删除 + 名称 / 可预约锁定；价格 / 时长 / 在售 / 下架仍可改
D10-f 术语 计次卡模板 / 列表 / 详情 / 扣次券文案的「大类」→「分组」（§11.1）

12.3 为什么不引用自定义分组（语义零漂移的关键）

引用主分组时，适用范围是唯一命中的集合运算，不需要任何新解析规则：

scope(card) = { p ∈ 项目桶 | p.primaryGroupId === card.scopeGroupId }

因为不变式 §3.3-1 规定 primaryGroupId 恒非空、恒唯一，所以：

  • 一个项目不可能被两张计次卡同时覆盖 → 不存在线上从未有过的「N:N 重复命中」；
  • 自定义分组怎么交叉（一个项目进 5 个组）都不影响计次卡 → 与线上语义零漂移。

反之，若引用自定义分组，就必须回答「项目同属两组时算谁的范围」（并集？交集？优先级？），等于把 §1.2 的「重复命中」问题复制到计次卡上 —— 明确不做。

12.4 数据模型（增量）

会员卡模板（线上计次卡）：

字段 类型 说明
scopeGroupId string | null 计次卡适用范围的主分组 id（g_<categoryId>）；建议命名，最终以联调契约为准。非空 = 圈定范围；null 仅作历史兜底
categoryId（旧） string 迁移期只读保留（同 §4.3 的 category 兼容期），新写入不再依赖

持卡实例（办卡时快照）：

字段 类型 说明
scopeItemIds string[] 办卡那一刻 scope(card) 的成员快照；此后不再随分组变化，用于扣次校验与退卡估值

「快照在实例、不在模板」是 D10-c 的直接结果，两者不可互换：模板也快照 → 「新增项目自动纳入范围」失效；实例也 live → 历史退卡金额会随分组变动漂移。

12.5 实时跟随的连带影响（必须一并处理，且必须告知商户）

A. 绑卡派生必须取并集 —— 本方案唯一的真坑

价目表/catalog.js 现有的绑卡派生只扫模板：

collectTemplateProjectRefs(templates)   // 只遍历 state.templates 的 projectItems / memberPrices
→ p.boundToCard = ids.length > 0

在「模板 live + 实例快照」组合下会出现这个顺序漏洞：

  1. 项目 A 属分组 G，计次卡 K 引用 G → A 是范围成员 → boundToCard = true（不可删）✅
  2. 把 A 移出 G（改主分组）→ 模板侧 K 不再覆盖 A → 若只扫模板，A 的 boundToCard 变 false
  3. 但已办卡实例的 scopeItemIds 仍含 A → 退卡估值仍要读 A
  4. → A 变成可删 → 历史卡估值出现孤儿引用（金额不可复现）

修正：

refs = 模板（projectItems ∪ memberPrices ∪ scopeGroupId → 当前组成员）
     ∪ 持卡实例（scopeItemIds）

即 boundToCard 表达的是「当前有任何引用」，而不是「只被模板引用」。

B. 绑卡面会随分组变宽（预期行为，但需要解释）

整组项目一次性全部变「已绑卡」→ 不可删除、名称 / 可预约锁定。商户想删组内某个项目时会撞 toast 该项目已绑定会员卡，不可删除，因此分组管理页需要前置说明：

「本组被 N 张计次卡作为适用范围，组内项目将不可删除」

C. 加 / 移项目即时改范围

  • 加入 G → 立即进范围 + 立即被锁（不可删）；移出 G → 退出模板范围，但实例并集仍在（见 A）。
  • 两步都不应弹窗（与 D3 一致、与 §6.2 的静默口径一致），可在分组管理页标注「N 张计次卡受影响」。

D. 范围为空必须拦截

G 被清空（成员为 0）→ 计次卡没有任何可扣项目。保存时必须拦截或明确提示「适用范围为空，请先向该分组加入项目」；不得静默存下空范围。

E. 只列项目桶的分组

计次卡扣的是项目，适用范围选择器只列 catalogGroups.project；产品桶分组不得出现在该选择器里（同 §6.5 产品权益页的桶隔离原则）。

F. 分组被删 / 主分组被改指时不得悬空

价目侧已有护栏（§3.3 不变量 5：删组前必须先指定迁入分组）。此处需额外要求：删除 / 改指前必须列出受影响的计次卡，避免「分组没了、卡的适用范围指向空气」。

12.6 迁移步骤（在 §4.1 之后追加，同样幂等、可回滚）

  1. 价目分组表建好后（source:'category' 组已就位），把每个线上计次卡模板的 categoryId 写成 scopeGroupId = 'g_' + categoryId（1:1）。
  2. 历史持卡实例：按办卡时点该大类的成员集回填 scopeItemIds（快照）—— 不可用「当前成员」回填，否则历史退卡估值会被改写。
  3. categoryId 保留只读（同 §4.3），并按 §9.3 每日 diff categoryId vs scopeGroupId。
  4. dry-run 校验（并入 §9.1 体检）： - 每个 scopeGroupId 命中分组表且非空； - categoryId 找不到对应分组的 → 落入 fallback 组并进人工清单； - 绑卡并集算出的引用数 = 迁移前「因计次卡而绑卡」的项目数（逐条 diff = 0）。
  5. 校验通过后才切读。
